# 기술 판단 사례와 기여 범위

이 문서는 실제로 재현한 결함, 적용한 선택과 검증 결과를 설명한다. 사후에 처음부터 정답을 알고 설계한 것처럼 정리하거나, AI와 함께 수행한 구현을 전부 수작업 기여로 표현하지 않는다.

## 작성자의 역할과 AI 활용

2026년 8월 30일부터 진행한 개인 프로젝트다. 작업 요청과 저장소에서 확인되는 역할은 다음과 같다.

| 구분 | 확인되는 작업 |
| --- | --- |
| 작성자 | 실시간 제조 운영 프론트엔드 프로젝트의 범위와 개선 우선순위를 정하고, 공개 데모로 표시하도록 기준을 정했다. 실제 화면의 잘림과 클릭 구분 문제를 캡처로 제보하고 재검증을 요구했다. GitHub 저장소를 생성하고 Vercel을 직접 연결했다. |
| AI 개발 도구 | 공개 자료 조사, 제품과 디자인 대안, 아키텍처 제안, 코드와 테스트 작성, 결함 재현, 문서 정리를 지원했다. 아래의 구현과 검증도 AI 도구를 활용했다. |
| 운영 검증 범위 | 합성 데이터와 로컬/공개 데모 환경에서 검증했다. 실제 제조 현장의 장비 연동과 장기 운영 검증은 수행하지 않았다. |

아래 사례는 설명할 수 있는 기술 근거다. 작성자의 상용 경력 연수나 실무 협업 경험을 대신하는 자료는 아니다.

## 사례 1. 빠른 차트가 센서 피크를 지우는 문제

### 발견과 재현

초기 샘플러는 같은 구간에서 다섯 센서의 정규화된 변화량을 합산하고 가장 높은 점수의 시점 하나를 골랐다. 대표 시점을 공유하므로 모든 트랙의 X축은 맞았지만, 그 사실만으로 각 센서의 극값이 보존되는 것은 아니었다.

2026년 8월 31일 검토에서 실제 앱과 같은 **18,000개 원본 시점 / 최대 1,800개 표시 시점** 조건의 반례를 만들었다. 장력은 300ms에서 50N에서 90N으로, 온도는 700ms에서 160°C에서 180°C로 튀도록 했다. 구간 내에서 더 높은 점수를 받은 온도 시점만 선택되어 장력 최댓값은 50N으로 낮아졌다. 현장 실측이 아니라 알고리즘 검증용 합성 입력이다.

수정 전에 [단위 테스트](../apps/web/src/lib/downsample.test.ts)와 [차트 전달값 테스트](../apps/web/src/components/SignalWorkbench.test.tsx)를 추가했다. 두 핵심 검사가 각각 장력 90N의 누락을 재현하며 실패했다.

### 선택한 정책

| 선택지 | 판단 |
| --- | --- |
| 변화량 가중치 조정 | 다른 센서 조합에서는 같은 경쟁이 남는다. 특정 반례만 통과하도록 점수를 조정하지 않았다. |
| 센서별로 따로 선택 | 각각의 극값을 남길 수 있지만 공통 시점을 유지하려면 별도 병합이 필요하다. |
| 모든 원본을 항상 차트에 전달 | 값을 줄이지 않지만 최대 표시 예산을 포기해야 한다. 원본은 메모리에 유지하고 표시만 요약하는 경계를 유지했다. |
| 공통 구간의 양 끝과 센서별 최솟값/최댓값의 시점 합집합 | 선택. 센서끼리 점수를 경쟁시키지 않으면서 공통 X축과 표시 예산을 함께 지킨다. |

[현재 샘플러](../apps/web/src/lib/downsample.ts)는 원본을 연속된 공통 구간으로 나눈다. 각 구간의 첫 시점, 마지막 시점과 다섯 센서의 최솟값/최댓값 시점을 합쳐 시간순으로 전달한다.

- 구간 하나의 후보 상한은 `2 + 5 × 2 = 12`개다.
- 표시 예산 1,800개에서는 `floor(1,800 / 12) = 150`개 구간을 사용한다.
- 같은 시점이 여러 조건을 만족하면 한 번만 남기므로 실제 출력은 1,800개보다 적을 수 있다.
- 유효한 시간순 입력에서 구간별 양 끝과 각 센서의 최솟값/최댓값을 원본 시점 그대로 보존한다.
- 축소가 필요한데 예산이 12개 미만이면 계약을 만족할 수 없으므로 오류로 처리한다.

차트의 센서별 `sampling: "lttb"`도 제거하고 모든 시리즈에 `sampling: "none"`을 지정했다. 앱에서 함께 선택한 시점을 차트가 다시 센서별로 줄이지 않도록 한 것이다.

### 결과와 감수한 한계

| 합성 반례 | 수정 전 차트 입력 | 수정 후 차트 입력 |
| --- | ---: | ---: |
| 좌측 장력 최댓값 | 50N | 90N |
| 온도 최댓값 | 180°C | 180°C |
| 공통 시점과 표시 예산 | 공유 시점, 1,800개 | 공유 시점, 최대 1,800개 |

피크 수정 시 관련 두 파일의 테스트 22개를 통과했다. 이후 건조기 구성 검사를 더해 현재 두 파일은 23개다. 다섯 센서의 서로 다른 최솟값과 최댓값, 구간 경계, 평탄 신호, 중복 시점 제거, 다양한 예산과 입력 불변성을 검사한다. 차트 테스트는 여섯 시리즈에 같은 시점이 전달되고 추가 샘플링이 꺼져 있는지 확인한다. 이는 전달값 검사이며 픽셀 단위의 최종 화면 검수를 대신하지 않는다.

**모든 국소 피크를 보존하는 알고리즘은 아니다.** 같은 센서의 같은 구간에서 90N과 80N 피크가 발생하면 더 작은 80N 피크는 생략될 수 있다. 반복 횟수, 지속 시간과 상세 파형을 요약 그래프만으로 확정하지 않는다. 현재 확대도 요약된 시리즈를 확대하는 동작이며 원본을 다시 샘플링하지 않는다. 이런 분석이 필요하면 표시 구간 기반 재샘플링이나 원본 구간 조회를 추가해야 한다.

이전의 “급격한 이상 신호도 보존된다”는 설명은 위 보장 범위로 좁혔다. 이전 알고리즘의 렌더 개선율도 현재 성능인 것처럼 재사용하지 않으며, [성능 전략](./PERFORMANCE.md)에서 측정 시점을 구분한다.

## 사례 2. 트랜잭션이 있어도 사라지는 작성 중 입력

### 발견한 문제

운영 화면을 여러 탭에서 열었을 때 두 종류의 유실을 구분해야 했다.

1. 두 탭이 저장된 문서 전체를 덮어쓰면 서로 다른 변경까지 잃을 수 있다.
2. DB 변경을 직렬화해도, 오래된 폼 전체를 저장하거나 다른 탭의 완료 상태에 맞춰 폼을 초기화하면 사용자 입력을 잃을 수 있다.

앞선 UI/UX 검토에서는 설정 변경 후 화면 왕복 시 값이 초기화되고, 다른 탭에서 작업을 완료하면 현재 탭의 미저장 결과가 사라지는 문제를 테스트로 재현했다. 당시 실패와 수정 기록은 [운영 화면 재검토](./OPERATIONS_UI_UX_REVIEW_2026-08-31.md)에 남아 있다.

### 선택과 이유

저장된 문서와 작성 중 입력의 수명을 분리했다.

- 저장된 업무 문서는 [IndexedDB 트랜잭션](../apps/web/src/lib/workspaceDatabase.ts) 안에서 최신 값 읽기 → 명령 적용 → 쓰기를 수행한다. 완료 이벤트 이후에만 성공을 표시한다.
- [업무 명령](../apps/web/src/domain/workspace.ts)은 편집한 필드와 편집 시작값을 받는다. 독립 필드는 병합하고 같은 필드의 외부 변경은 충돌로 알린다.
- [초안 스토어](../apps/web/src/store/workspaceDraftStore.ts)는 현재 탭의 입력을 유지한다. 화면 이동이나 다른 탭의 완료 때문에 자동 삭제하지 않는다.
- 저장 또는 명시적 취소가 초안 삭제 시점이다. 더 이상 저장할 수 없는 기록의 입력도 별도 영역에서 확인하고 지울 수 있다.

폼 전체를 외부 변경마다 강제로 다시 생성하는 방법은 상태를 맞추기 쉽지만 작성 중 입력을 잃는다. 반대로 외부 변경을 전부 무시하면 이미 완료된 작업에 저장을 시도한다. 저장 상태는 최신으로 읽되 입력은 별도로 보관하는 절충을 선택했다.

### 검증과 비용

[회귀 테스트](../apps/web/e2e/workspace-review.spec.ts)는 독립 설정 변경의 병합, 동일 필드 충돌 안내, 다른 탭의 작업 완료 후 미저장 결과 보존을 확인한다. 모바일에서는 500자 결과 작성 → 다른 화면 이동 → 복귀 → 작업 완료 → 별도 이상 종결까지 검사한다.

초안은 현재 탭 메모리에만 남는다. 새로고침 복원이나 다른 기기 공유를 구현한 것이 아니며 이탈 경고도 브라우저의 강제 종료까지 막지 못한다. 이 비용을 화면과 문서에서 알린다. 다중 사용자 제품으로 확장할 때는 서버 버전 검사, 권한, 초안 보관 정책과 감사 로그를 별도로 설계해야 한다.

## 사례 3. 재사용을 두 번째 설비로 검증하기

### 문제와 선택

공통 컴포넌트가 있다는 사실만으로 다음 설비의 구현이 쉬워진다고 말할 수 없었다. 기존 상세 진단은 COATER-02뿐이었고 패널과 온도 기준, 안전 문구가 화면에 고정돼 있었다.

두 번째 사례로 DRYER-02를 연결했다. 진단 화면을 복사하는 대신 표시 패널과 기준값, 이벤트, 안내를 프로필로 분리했다. 건조기에는 장력을 숨기고 온도, 속도와 후단 검사 결과를 표시한다. 안전 체크리스트는 프론트엔드 설정과 분리해 서버도 동일한 공유 계약으로 검사한다.

가장 중요한 추가 비용은 데이터의 경계였다. 이름만 바꾸고 이전 버퍼를 유지하면 다른 설비를 판단하게 된다. 설비 전환 때 소켓과 버퍼를 교체하고 HTTP 응답과 스트림 태그를 검사했다. 이전 요청의 늦은 응답은 새 설비에 반영하지 않으며 작업 발행 결과도 현재 설비로 한정해 복원한다.

### 검증과 한계

[재사용 E2E](../apps/web/e2e/equipment-reuse.spec.ts)는 두 설비의 실제 이력과 스트림 전환, 건조기 안전 확인과 작업 완료, 발행 결과 복원과 미확인 요청 보호를 검사한다. [구성 비교표](./EQUIPMENT_REUSE.md)에서 공통 파일과 설비별 변경 지점을 확인할 수 있다.

이는 같은 다섯 신호 어휘 안에서 두 가지 표시 구성을 지원한 결과다. 새로운 센서 스키마나 현장 커넥터를 설정 한 줄로 지원하지 않는다. 두 번째 현장의 구축 기간 단축이나 고객사 적용 성과도 측정하지 않았다.

## 사례 4. 차트가 빠른 것과 전체 흐름이 빠른 것은 다르다

### 빠졌던 측정 구간

기존 전후 비교는 샘플링과 Canvas 동기 렌더를 설명했지만 네트워크, JSON 검증, 500ms 수신 배치와 React 갱신은 빠져 있었다. 따라서 그 개선율을 전체 앱의 속도 향상으로 사용하지 않았다.

후속 계측은 실제 프로덕션 빌드에 opt-in 기록 지점을 넣었다. 설비 클릭에서 코드 로딩과 이력 조회를 거쳐 차트가 반영되는 구간, 실시간 패킷의 배치 대기, 상태 반영 이후 차트, 확대/이동, API 발행 후 IndexedDB 저장과 결과 표시를 나눴다. 실제 앱과 같은 Vite 버전을 사용하며 개별 표본과 실행 소스 해시를 남긴다.

### 결과를 해석하는 기준

차트의 `finished` 이벤트 후 두 `requestAnimationFrame`으로 관측한 것은 렌더 프레임 기회다. 화면 픽셀이 실제로 표시된 완료 시각은 아니다. 배치 대기가 포함된 수신 지연을 Canvas 처리 비용과 혼동하지 않도록 두 수치를 함께 기록한다.

설비별 세 번의 시작 표본으로는 안정적인 p95를 주장하지 않는다. 반복 수신과 입력 표본도 한 장비의 합성 워크로드이며 독립된 실제 사용자 표본이 아니다. 수치와 표본 수, 측정하지 않은 조건은 [성능 문서](./PERFORMANCE.md)에 공개한다.

### 실제 관측과 후속 판단

로컬 반복 측정에서 COATER-02의 배치 최초 수신 → 차트 반영 중앙값은 470.2ms였지만, 배치 상태 반영 이후는 43.5ms였다. 차트 렌더만 줄여서는 의도한 500ms 배치 대기가 없어지지 않는다. 수신 지연 목표를 더 낮추려면 배치 주기와 메인 스레드 비용을 함께 조정하고 다시 측정해야 한다. 이번에는 지연 목표를 임의로 바꾸지 않았다.

첫 180초 측정은 보존/표시 개수 상한을 지켰지만 힙 API가 37회 모두 같은 값을 반환했다. 이 값만으로 메모리가 안정적이라고 결론 내리지 않았다. 후속으로 CDP 힙과 주기적 계측 회수를 추가하고 100,000개 이력, CPU 4배 제한, 60분 수신을 결합했다.

### 고밀도 입력에서 드러난 의미 손실

첫 구현은 100,000개 중 최신 20,000개만 보존했다. 개수 상한은 지켰지만 18ms 간격 입력에서는 약 6분만 남아 DRYER-02의 이상 시점과 현장 검증 버튼이 사라졌다. 빠른 코드가 판단 근거를 훼손한 사례였다.

전체 30분을 센서별 극값과 구간 경계로 최대 20,000개에 요약하도록 수정했다. 시작 인덱스는 이진 탐색으로 찾고 샘플러가 원본의 후행 구간을 직접 읽게 해 약 100,000개 포인터의 중간 `slice`를 피했다. 단위 테스트에서 100,000개 응답의 과거 결함률 극값, 시간 경계와 최신 실시간 시점 병합을 확인했고 두 설비의 전체 흐름을 다시 실행했다.

차트 단독 비교에서는 CPU 4배 제한에서 100,000개 원본의 Canvas 렌더 중앙값 724.2ms가 실제 1,732개 요약에서 32.7ms로 줄었다. 샘플링과 옵션 준비까지 포함하면 777.1ms에서 98.8ms였다. 이 95.5%와 87.3%는 같은 합성 차트 실행의 전후 비교이며 앱 전체 개선율이 아니다.

60분 전체 앱 실행은 최신 수신→차트 반영 7,200개 표본의 p95 303.8ms, 상태 반영→차트 반영 p95 79.2ms였다. Long Task 29건과 강제 GC 뒤 6.6MB 힙 증가도 함께 남겼다. 오류와 계측 유실은 없었지만 이 결과로 누수 부재, 실제 저사양 단말이나 현장 SLA를 주장하지 않는다. 이상 시점이 30분 범위를 벗어난 뒤에는 포커스와 새 작업 발행을 보류하는 정상 상태까지 검증했다.

## 남은 검토 기준

- 현장 네트워크와 물리 저사양 단말, 다중 사용자 부하, 8시간 메모리와 화면 합성까지 검증할 것
- 다른 태그 스키마와 실제 커넥터를 적용할 때 재사용 비용을 다시 측정할 것
- 현장 사용성, 실제 업무 승인과 운영 효과는 실제 사용자와 데이터가 있을 때 검증할 것

위 항목은 아직 수행한 성과가 아니다. 두 설비의 공개 데모 구현과 로컬 성능 측정, 최종 화면 캡처 및 공개 배포 확인은 [릴리스 검증 기록](./RELEASE_REVIEW_2026-08-31.md)에서 구분한다.
