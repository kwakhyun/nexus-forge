# 성능 측정과 시계열 요약

두 종류의 근거를 구분한다. **차트 전후 비교**는 고정된 합성 차트 조건의 개선율이며, **전체 흐름 계측**은 측정 시점 실제 앱의 경로별 관측값이다. 후자에는 최적화 전 동일 조건의 앱 표본이 없으므로 전후 개선율을 만들지 않는다.

이 결과의 측정 소스는 `20ad702`에 포함됐다. 이후 [직접 화면 검수](./BROWSER_REVIEW_2026-08-31.md)와 [최종 회귀 검사](./FINAL_VERIFICATION_2026-08-31.md)에서 바로가기, 모바일 상세와 메뉴 이동, 생산 집계를 수정했지만 전체 앱 성능을 다시 측정하지 않았다. 따라서 원본의 24개 해시가 후속 변경 파일까지 일치한다고 해석하지 않는다. 차트 단독 측정이 사용하는 시계열 샘플러는 이 후속 수정에서 변경하지 않았다.

## 차트 단독 전후 비교 — 2026년 8월 31일

[최신 원본 JSON](./benchmarks/performance-2026-08-31.json)은 Apple M2, macOS Darwin 25.6.0, Node.js 22.21.0, Chromium 151.0.7922.34 환경의 측정이다. 화면 1200×700, DPR 1, 애니메이션 비활성화, Canvas 4개 패널과 6개 시리즈 조건을 사용했다. KB는 1,000바이트 기준이다.

| 측정 항목 | 원본/전체 import 기준 | 현재 요약/Core import | 변화 |
| --- | ---: | ---: | ---: |
| ECharts 전용 번들, minified | 1,132.1KB | 589.9KB | 47.9% 감소 |
| ECharts 전용 번들, gzip | 380.2KB | 199.5KB | 47.5% 감소 |
| Canvas 동기 렌더 중앙값 | 33.2ms | 6.3ms | 81.0% 감소 |
| Canvas 동기 렌더 p95 | 36.3ms | 8.8ms | 각 60회 표본 |
| 데이터 준비 + 동기 렌더 중앙값 | 35.4ms | 9.3ms | 73.7% 감소 |
| 데이터 준비 + 동기 렌더 p95 | 38.6ms | 14.2ms | 각 60회 표본 |
| 전달하는 원본 시점 수 | 18,000개 | 1,208개 | 예산은 최대 1,800개 |

표의 개선율은 같은 실행 안의 기준/현재 조건 비교다. 과거 실행 결과와 이번 결과를 나눠 개선율을 계산하지 않는다.

### 재현 방법과 측정 구간

```bash
npm ci
npm run benchmark:performance
```

[측정 스크립트](../scripts/benchmark-performance.mjs)는 결과를 표준 출력으로 내보낸다. 기록된 스냅샷을 자동 덮어쓰지 않는다.

1. 같은 Vite minify와 gzip 조건으로 전체 ECharts import와 Core 모듈 import를 비교한다. 이는 전체 웹 번들 크기가 아니라 ECharts 전용 비교다.
2. 앱의 `apps/web/src/lib/downsample.ts`를 직접 빌드해 호출한다. 별도로 복사한 샘플러를 사용하지 않으며, 실행한 원본 파일의 SHA-256을 결과에 보관한다.
3. 합성 입력은 18,000개 시점과 다섯 센서다. 차트에는 온도 설정값까지 여섯 시리즈를 표시한다. 원본 시점 18,000개, 센서값 90,000개, 차트 입력 좌표 108,000개를 같은 단위로 혼용하지 않는다.
4. 기준과 요약 차트의 사건 시각은 같은 원본 시각으로 고정한다. 두 조건 모두 연결 커서, DataZoom, 이상 영역과 이벤트 기준선을 포함하고 `sampling: "none"`으로 추가 축소를 끈다.
5. 각 조건을 3회 예열하고 60회 반복한다. 원본과 요약의 렌더 순서를 번갈아 실행한다. 최종 기록은 이 작업의 단위/E2E 테스트와 겹치지 않는 독립 실행이며, 다른 시스템 부하까지 통제한 실험은 아니다.
6. **동기 렌더:** `setOption`부터 zrender `flush` 종료까지 측정한다. 브라우저가 화면 합성까지 끝낸 시간이 아니다.
7. **데이터 준비:** 기준은 차트 옵션 생성, 현재 조건은 실제 샘플러 실행과 차트 옵션 생성을 포함한다. 샘플러만의 중앙값은 2.4ms, p95는 6.7ms다.
8. **준비 + 렌더:** 같은 반복의 준비 시간과 렌더 시간을 합한 표본에서 중앙값과 p95를 계산한다. 각각의 중앙값을 단순히 더한 결과가 아니다.

원본 JSON에는 각 조건의 60개 표본, 실제 출력 개수와 예산, 환경, 샘플러 해시가 있다. 중앙값과 p95는 오름차순 표본의 nearest-rank 방식으로 계산한다. 단일 장비의 제한된 합성 표본이며 모집단 지연이나 현장 SLA로 일반화하지 않는다.

### 이 차트 비교에 포함하지 않은 범위

- 네트워크 전송과 응답 파싱, 실시간 수신부터 화면 표시까지의 전체 지연
- React 렌더링, 500ms 배치 대기, 브라우저 화면 합성
- 실제 앱에서의 지속적인 증분 갱신, 확대/이동 및 입력 반응성
- 다중 설비, 저사양 현장 단말, 장시간 실행의 메모리와 프레임 드롭
- 이번에 추가한 운영 화면 전체의 성능

위 결과는 샘플러 변경 이후의 차트 벤치마크다. 전체 앱의 수치는 아래 별도 계측을 따른다. 두 실험은 차트 옵션과 렌더 완료의 정의가 달라 직접 나눠 개선율을 계산할 수 없다.

# 계측기 연결 확인용 짧은 실행. 포트폴리오의 본 측정과 구분한다.

기본값은 설비별 새 브라우저 컨텍스트 3회, 각 30초 관찰, 별도 COATER-02 연속 180초다. 기존 결과 파일은 덮어쓰지 않으며 파일이 존재하면 실패한다. 새 컨텍스트에서 공정 개요를 열고 설비 버튼을 선택한 뒤 이력, 실시간 수신, 확대/이동과 발행 저장을 확인한다. 각 30초 실행에는 확대, 이전 구간, 이상 구간, 실시간 따라가기를 7회씩 수행한다. 순서는 설비별로 교차한다. 180초 관찰에서는 차트 입력 없이 수신을 유지한 뒤 작업 발행을 확인한다.

웹 워크스페이스의 Vite 6.4.3을 직접 해석해 빌드한다. 루트에서 우연히 선택되는 다른 Vite 버전을 사용하지 않는다. Apple M2, Chromium headless, 1440×1024, DPR 1, 로컬 HTTP/WS, 정적 응답 no-store, Sentry 비활성 조건이다. CPU나 네트워크를 인위적으로 제한하지 않는다. 본 측정 중 개발 서버와 이 저장소의 다른 테스트·빌드는 실행하지 않았으며 OS 전체의 부하까지 통제한 실험은 아니다.

### 구간 정의

| 원본 측정 키 | 포함하는 구간 |
| --- | --- |
| `equipment_click_to_history_frame_opportunity` | 설비 클릭 핸들러 → 경로 변경/진단 코드 로딩 → 이력 조회/검증 → 상태 갱신/요약/차트 반영. 최초 공정 개요 접속 시간은 제외 |
| `history_fetch_parse_validate` | 이력 요청 시작 → 서버 합성 생성/전송, JSON 파싱과 응답 검증 완료 |
| `history_request_to_frame_opportunity` | 이력 요청 시작 → 첫 이력 차트 반영. 단독 스트림 몇 점이 먼저 그려진 시각으로 대체하지 않음 |
| `stream_oldest_receive_to_frame_opportunity` | 배치에서 가장 먼저 받은 시점의 메시지 수신 → 차트 반영. 500ms 배치 대기 포함 |
| `stream_latest_receive_to_frame_opportunity` | 같은 배치에서 마지막으로 받은 시점의 메시지 수신 → 차트 반영. 서버 생성부터의 지연과는 다름 |
| `stream_batch_wait` | 가장 먼저 받은 시점의 수신 → 배치의 스토어 반영 직전 |
| `batch_commit_to_frame_opportunity` | 배치 반영 직전 → 링 버퍼/React/샘플링/차트 반영 |
| `chart_effect_to_frame_opportunity` | 차트 effect 시작 → 옵션 생성/Canvas 처리와 후속 프레임. effect 이전 React 렌더·샘플링은 제외 |
| `interaction_*_to_frame_opportunity` | 차트 버튼 핸들러 → 변경된 범위의 반영. OS 입력 도착부터의 지연은 제외 |
| `verification_request_and_persistence` | 발행 처리 시작 → 미확인 요청 저장, POST 응답 검증, 업무 기록 IndexedDB 저장 완료 |
| `verification_submit_to_result_frame_opportunity` | 같은 발행 처리 시작 → 저장 후 결과 화면의 후속 프레임 |

여기서 **차트 반영은 `finished` 이벤트 후 두 번의 rAF로 관찰한 렌더 프레임 기회**다. 실제 픽셀이 화면에 합성된 시각이나 프레임 드롭, 60fps 달성을 측정한 것이 아니다. rAF는 화면 그리기 이전의 콜백이므로 이 구분이 필요하다. [MDN requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)

`loopback_sample_age_at_frame_opportunity`는 같은 호스트의 서버 생성 시각과 브라우저 시각 차이를 보조적으로 기록한다. 현장 장비 간 시계 동기화나 WAN 지연으로 해석하지 않는다. 스트림 집계의 관찰 시작점은 이력과 최소 세 번의 실시간 차트 반영 이후다. 관찰 구간에 **시작한** 측정값만 steady 집계에 포함하므로 키별 표본 수는 경계에서 조금 다를 수 있다.

### 원본과 통계 해석

각 실행의 개별 표본, 집계, 환경, 의존성 버전, 기준 커밋과 dirty 여부, 핵심 소스 SHA-256을 원본 JSON에 보관한다. 중앙값은 짝수 N일 때 중앙 두 값의 평균, p95는 nearest-rank다. N이 20 미만이면 p95를 `null`로 남긴다. 세 번의 초기 진입과 발행 표본은 중앙값과 범위만 해석한다. 단일 장비의 반복 시점은 독립 사용자나 장비 표본이 아니다.

PerformanceObserver로 50ms 이상 메인 스레드 Long Task도 기록한다. 연속 관찰 구간과 초기 진입을 포함한 전체 구간을 분리한다. [MDN Long Tasks](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceLongTaskTiming)

네이티브 Event Timing은 16ms 이상의 항목만 관찰하며 시간은 8ms 단위로 반올림될 수 있다. 임계값 미만 입력이 원본에 없으므로 이를 포함한 전체 입력 분포나 프로덕션 INP로 표현하지 않는다. [MDN Event Timing](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceEventTiming)

180초 연속 수신에서 힙은 강제 GC 없이 약 5초 간격의 `performance.memory` 값으로 관찰한다. Chromium 전용의 근사치이며 다른 브라우저와 비교 가능한 정밀 메모리 지표가 아니다. 이번 3분 실행은 37회 모두 같은 값을 반환해 단기 힙 추이조차 판단하지 않는다. 확인한 것은 원본/표시 개수의 상한이며 메모리 누수 부재가 아니다. 장시간 관찰과 더 정밀한 메모리 측정은 남아 있다. [MDN performance.memory](https://developer.mozilla.org/en-US/docs/Web/API/Performance/memory)

일반 빌드는 계측 전역 객체나 PerformanceObserver를 생성하지 않는다. 계측 활성/비활성, 중복 기록 방지, 배치 구간 분리, 숨김/폐기된 차트 제외, 저장 후 결과 기록은 [전용 테스트](../apps/web/src/observability/performanceProbe.test.ts)로 확인한다. 계측 데이터는 로컬 JSON으로만 저장하며 외부 서비스로 전송하지 않는다.

### 여전히 측정하지 않은 범위

- 공개 Vercel CDN과 Function의 시작 지연, WAN과 산업용 네트워크
- 실제 다중 사용자 동시 부하, 여러 설비의 동시 차트 구독, 저사양 단말
- 8시간 교대 운영, 장기간 센서 저장과 누수, 화면 합성 및 실제 입력 장치 지연
- 전체 운영 메뉴의 모든 상호작용 성능과 실제 사용자 RUM
- 계측 비활성 빌드와 활성 빌드 사이의 비용 차이. 모든 현재 앱 표본은 동일한 계측 조건

이 측정은 설비 진단과 작업 발행 경로의 로컬 계측이다. 고객사 운영 성과나 SLA 보증, 두 설비의 성능 우열 비교가 아니다. 250ms 수신과 500ms 배치 타이머의 위상도 최신 시점의 대기 시간을 바꾼다.

## 현재 요약 정책과 보장

[기술 판단 사례](./ENGINEERING_CASE_STUDIES.md)에 변화량 방식의 실패와 대안 선택을 기록했다.

- 최대 표시 예산은 1,800개다. 입력이 예산 이내이면 축소하지 않는다.
- 축소할 때 원본 시점을 150개 연속 구간으로 나누고, 각 구간의 양 끝과 다섯 센서의 최솟값/최댓값 시점을 합친다.
- 한 구간의 최대 후보는 `2 + 5 × 2 = 12`개다. 같은 시점은 한 번만 남겨 전체 출력이 예산을 넘지 않는다.
- 입력은 API 경계에서 유효성이 검사된, 시간순의 유한 센서값이다. 출력은 원본 객체와 시각을 유지하며 입력을 변경하지 않는다.
- 차트의 여섯 시리즈가 같은 시점 배열을 사용하고, ECharts의 센서별 재샘플링은 비활성화한다.
- 보장 범위는 **공통 구간의 경계와 센서별 극값**이다. 작은 국소 피크, 반복 횟수와 지속 시간까지 보존하지 않는다.
- 확대는 요약 시리즈의 확대다. 작은 구간의 원본 회복이 필요하면 표시 구간 기반 재샘플링이나 원본 조회가 별도로 필요하다.

단위 테스트는 같은 구간의 장력 90N과 온도 180°C 피크, 다섯 센서의 상하 극값, 경계, 평탄 신호, 출력 예산을 검사한다. 더 작은 국소 피크가 생략될 수 있는 반례도 남겨 보장 범위가 넓어지지 않도록 한다.

## 기타 적용한 최적화

- 진단과 다섯 운영 라우트를 `React.lazy`로 분리한다. 공정 개요 진입에서 차트 코드를 불러오지 않는다.
- ECharts Core에서 사용하는 차트, 축과 상호작용 모듈만 등록한다.
- WebSocket은 250ms로 수신하고 500ms 단위로 모아 Zustand와 차트에 반영한다.
- 순환 인덱스를 쓰는 링 버퍼로 최근 30분, 최대 20,000개 센서 시점을 보관한다. 개수 상한이 전체 앱의 메모리 누수 부재를 증명하지는 않는다.
- Sentry는 DSN이 설정된 경우에만 동적으로 로드한다.
