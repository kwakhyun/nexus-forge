# API와 스트림 계약

모든 설비, 인시던트, 작업 지시는 공개 데모의 합성 데이터입니다. 실제 담당자에게 작업을 전송하거나 설비를 제어하지 않습니다.

## REST

### `GET /health` 또는 `GET /api/health`

서버 상태와 시간, 배포 커밋을 반환합니다. 로컬 통합 서버의 `clients`는 현재 프로세스에 연결된 WebSocket 클라이언트 수이며 `clientCountScope`는 `process`입니다. REST와 스트림이 별도 Function인 공개 Vercel 데모에서는 전역 접속자 수를 추정하지 않습니다.

```json
{
  "status": "ok",
  "clients": null,
  "clientCountScope": "unavailable",
  "release": "9c81818dbb7acf500ccbfcf65fe3ea49e06ddd7b",
  "now": 1788041164730
}
```

`release`는 배포 검증에서 요청한 커밋과 실제 공개 커밋이 같은지 확인하는 기준입니다.

### `GET /api/plant/summary`

공장과 선택 라인, 네 개 공정 단계, 코팅 1호와 2호 라인의 12대 설비, 활성 인시던트, 원인 후보와 근거를 반환합니다. 공정 개요, 진단과 업무 기록 초기화는 같은 Query 캐시를 사용하고 10초 간격으로 갱신합니다. 갱신 실패 시 마지막 현황을 유지하되 최신 정보가 아니라는 안내와 재시도 경로를 표시합니다. 이 API의 합성 이상 상태와 브라우저에서 사용자가 기록하는 처리 상태는 별도입니다.

`activeIncident`는 개요의 주 대상인 COATER-02입니다. `diagnosticIncidents`는 COATER-02와 DRYER-02의 서로 다른 이상 ID와 근거를 담습니다. 공유 타입에서는 이전 데이터와의 호환을 위해 선택 항목이며, 없을 때는 `activeIncident`만 진단 대상으로 사용합니다. 새 런타임은 두 항목을 모두 반환합니다.

### `GET /api/production`

`ProductionResponse`를 반환합니다. `source`는 항상 `simulation`이며 `from`, `to`, `generatedAt`은 밀리초 타임스탬프입니다. 완료된 최근 14일, 2개 코팅 라인의 시간별 실적 672건을 제공합니다. `to`는 현재 시각 이전의 정시이며 진행 중인 시간대는 제외합니다. 같은 시간대와 라인에는 같은 합성값을 생성하므로 인스턴스 재시작만으로 실적이 바뀌지 않습니다.

각 `ProductionRun`은 `id`, `lineId`, `startedAt`, `endedAt`, `plannedMeters`, `inspectedMeters`, `rejectedMeters`, `downtimeMinutes`로 구성합니다. 단위는 코팅 길이 m와 정지 시간 분이며 완성 셀 수량이 아닙니다.

클라이언트는 응답 범위, 고유 ID, 두 라인 ID, 정시 기준 1시간 구간, 라인/시간대 중복, 유한한 비음수 측정값, 불량 길이 ≤ 검사 길이, 구간 길이 이내의 정지 시간을 검증합니다. 최근 24시간 또는 7일과 직전 동기간을 집계하며, 불량 판정 비율은 `불량 길이 합계 / 검사 길이 합계`입니다. 데이터가 없는 분모를 0%로 표시하지 않습니다. 일부 시간대나 라인 자료가 빠지면 부분 집계를 안내하고 증감 비교를 보류하며, 조회 결과가 없는 라인은 별도 빈 상태로 표시합니다.

### `GET /api/equipment/:equipmentId/history?intervalMs=100`

`COATER-02`와 `DRYER-02`의 최근 30분 센서 이력을 반환합니다. 응답은 `equipmentId`, `intervalMs`, `generatedAt`, `points`입니다. 나머지 설비 ID는 `404 equipment_history_unavailable`이며 다른 설비의 데이터를 대신 반환하지 않습니다. 간격은 50ms에서 1,000ms 사이로 제한하고, 없거나 숫자가 아니면 100ms를 사용합니다.

웹 클라이언트는 요청과 응답의 설비 ID 일치, 유효한 숫자, 최소 두 시점, 단조 증가하는 타임스탬프를 확인합니다. 비어 있거나 잘못된 이력은 성공 응답이어도 분석 가능한 데이터로 인정하지 않습니다. 설비별 표시 구성은 달라도 현재 전송 계약은 공통 다섯 센서 필드입니다.

### `POST /api/verifications`

담당자, 발행 시각, 완료 기한이 포함된 가상 작업 지시를 반환합니다. 요청 본문은 16KiB, 인스턴스별 최근 기록은 100건으로 제한합니다. 알려진 인시던트 ID와 공유 계약 `verificationChecklist(equipmentId)`의 안전 확인 세 항목이 모두 필요합니다. COATER-02는 `VERIFICATION_CHECKLIST`, DRYER-02는 `DRYER_VERIFICATION_CHECKLIST`를 사용하며 서로 바꿔 제출할 수 없습니다.

```json
{
  "requestId": "c4bd39c1-77e9-478c-a4e0-446c1f8051bd",
  "incidentId": "INC-20260829-042",
  "requestedBy": "라인 엔지니어 김현수",
  "assignee": "설비 보전팀 이민호",
  "checks": [
    "댄서 롤 안전 가드와 작업 동선에 이상이 없는지 확인했습니다.",
    "현장 작업 표준에 따른 점검 가능 운전 조건을 확인했습니다.",
    "현장 작업자에게 점검 목적과 절차를 공유했습니다."
  ]
}
```

성공 응답은 위 요청 필드에 아래 필드를 추가한 `VerificationRecord`입니다.

DRYER-02의 이상 ID는 `INC-20260831-DRYER-02`입니다. 첫 안전 항목은 `고온부와 건조로 내부에 접근하지 않는 외부 계기 점검임을 확인했습니다.`로 달라지고 나머지 두 항목은 같습니다. 위 JSON은 COATER-02 요청 예시입니다.

```json
{
  "id": "WO-12AB34CD",
  "status": "issued",
  "issuedAt": 1788022800000,
  "dueAt": 1788024600000
}
```

웹은 논리적 발행 요청마다 `requestId`를 만들고 통신 오류 후에도 같은 ID와 본문으로 재시도합니다. 같은 인스턴스에 기록이 남아 있으면 최초 발행은 `201`, 재시도는 같은 기록과 `200`을 반환합니다. 같은 ID로 다른 내용을 보내면 `409 request_id_conflict`, 필수 안전 확인이 부족하면 `400 safety_checks_required`, 알려지지 않은 인시던트면 `404 incident_not_found`입니다.

`requestId`는 계약상 선택 항목이지만 생략하면 중복 방지가 적용되지 않습니다. **중복 방지는 인스턴스 메모리에 남아 있는 최근 100건에 한정**됩니다. 재시작, 다른 인스턴스로의 라우팅, 기록 만료 이후의 exactly-once 처리를 보장하지 않습니다. 상용 작업 지시에는 영속 저장소의 고유 키와 트랜잭션이 필요합니다.

### `GET /api/verifications`

현재 Function 인스턴스가 보관하는 `VerificationRecord[]`를 최신순으로 반환합니다. 최대 100건이며 재시작 시 사라지고 다른 인스턴스와 공유되지 않습니다. 정비 관리 화면의 복원에 이 목록을 사용하지 않습니다. 브라우저가 발행 응답을 받은 뒤 저장한 IndexedDB 기록이 해당 브라우저의 작업 목록입니다. 서버 응답의 `status: issued`는 발행 사실만 표현하고, 점검 진행/완료와 이상 종결은 브라우저 업무 모델에 저장합니다.

### 브라우저 업무 명령의 경계

이상 확인, 담당자 변경, 점검 시작/완료, 이상 종결, 알림 읽음과 설정 변경은 서버 REST 엔드포인트가 아닙니다. `apps/web/src/domain/workspace.ts`의 검증된 명령을 `workspaceDatabase`가 IndexedDB 트랜잭션으로 저장합니다. 서버 API나 서버 감사 로그를 구현한 것으로 설명하지 않습니다.

설정 명령의 `expected`는 사용자가 편집한 필드의 시작값입니다. 이 필드들만 최신 설정에 적용하며, 현재 값이 시작값 및 제출값과 모두 다르면 충돌로 거부합니다. 담당자 명령의 `expectedAssignee`도 같은 방식으로 오래된 변경을 방지합니다. 저장 전 입력은 별도의 탭 메모리이며 API 요청이나 공유 DB 문서가 아닙니다.

발행 요청 본문을 먼저 저장하고, REST 응답을 받은 뒤 작업 기록 추가, 이상 상태 변경, 알림 생성과 미확인 요청 해제를 하나의 트랜잭션으로 수행합니다. 저장 실패 시 성공 화면을 표시하지 않고 미확인 요청을 유지합니다. 새로고침 후 같은 요청으로 재확인할 수 있지만, 서버 재시작/다중 인스턴스의 중복 실행 한계는 그대로입니다.

브라우저별 미확인 요청은 동시에 한 건입니다. 다른 설비에 미확인 요청이 있으면 새 작업 발행을 막고 해당 설비의 재시도를 안내합니다. 확정된 작업 이력은 설비별로 조회하고 복원합니다.

### 클라이언트 오류 처리

- REST 요청은 10초 타임아웃과 Query의 취소 신호를 적용합니다.
- 공정 현황, 센서 이력, 생산 실적, 작업 지시 응답은 렌더링 전에 형식을 검증합니다.
- 발행 중에는 입력 변경과 모달 닫기를 막습니다. 응답 유실 뒤에는 요청 ID와 본문을 브라우저에 저장한 상태로 재시도합니다. 결과 미확인 중에는 담당자 변경과 데이터 초기화를 보류합니다.
- 화면의 역할 선택은 UX 체험용입니다. 인증과 서버 권한 검증을 대체하지 않습니다.

## WebSocket `/stream`

- `/stream`은 COATER-02를 구독합니다. `?equipmentId=COATER-02` 또는 `?equipmentId=DRYER-02`로 대상을 지정할 수 있습니다. 지원하지 않는 ID는 코드 `1008`로 연결을 닫습니다.
- `hello`: 스트림 ID, 전송 간격, 서버 시간, `equipmentId`
- `sensor.point`: 센서 시점과 증가하는 시퀀스 번호, `equipmentId`
- `heartbeat`: 연결 생존 확인용 서버 시간

센서 시점은 `webTensionLeft`, `webTensionRight`, `ovenTemperature`, `lineSpeed`, `defectRate`를 같은 타임스탬프로 묶습니다. 공유 계약은 `packages/contracts/src/index.ts`에 있습니다.

새 런타임은 항상 설비 ID를 보냅니다. 태그 없는 기존 프레임은 기본 COATER-02 구독에서만 허용하며 DRYER-02로 해석하지 않습니다. 설비 ID가 구독 대상과 다르면 클라이언트는 코드 `4002`로 닫습니다. 설비 전환 시 이전 소켓과 배치를 정리하고 늦게 도착한 과거 설비 데이터는 스토어에서도 거부합니다.

유효한 센서 값이 5초 넘게 오지 않으면 하트비트가 계속 오더라도 `센서 데이터 지연`으로 표시합니다. 모든 유효 프레임이 35초 넘게 끊기면 소켓을 닫고 지수 백오프로 다시 연결합니다. 형식이 잘못된 프레임도 정상 데이터로 인정하지 않습니다.

이력은 100ms, 실시간 전송은 250ms 간격입니다. 웹은 500ms 단위로 반영하고 최근 30분과 최대 20,000개 시점 제한을 함께 적용합니다. 늦게 도착한 이력 응답은 응답 대기 중 수신한 최신 시점을 덮어쓰지 않습니다.
