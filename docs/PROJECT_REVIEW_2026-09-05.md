# 프로젝트 검토 — 2026년 9월 5일

> 이 문서는 수정 전 검토 기록입니다. 후속 구현과 검증 결과는 [개선 완료 기록](./IMPROVEMENTS_2026-09-05.md)에 정리했습니다. 아래 줄 번호는 검토 당시 기준입니다.

당시 로컬 소스(`6f1e97b`)를 대상으로 오류, 디자인, 구조와 최적화 여지를 검토했다. 구현 파일은 수정하지 않았다. 아래의 P1은 업무 복구를 막는 우선 수정 항목, P2는 특정 조건의 기능 문제, P3는 후속 개선 항목이다. 테스트 실행 실패와 제품 오류는 구분했다.

## 1. P1 — 이력이 만료되면 미확인 작업 요청을 복구할 수 없음

**근거:** `apps/web/src/components/VerificationDialog.tsx:42`, `:210`, `apps/web/src/components/CauseRail.tsx:149`, `apps/web/src/lib/workspaceDatabase.ts:120`.

작업 발행 응답이 유실되면 `pendingVerification`을 남겨 같은 요청으로 다시 확인하도록 설계되어 있다. 그러나 재확인 버튼에도 신규 발행 조건인 `canIssue`를 적용한다. 이후 이상 발생 시점이 최근 30분 이력을 벗어나면 `DiagnosticsPage`가 `out-of-range`로 판단하면서 재확인을 비활성화한다. 대화상자를 닫은 상태에서는 CauseRail의 진입 버튼도 비활성화된다. 설정과 저장소 계층은 미확인 요청이 있다는 이유로 초기화를 거부한다.

재현 순서: 작업 발행 후 응답 유실 → 미확인 요청 유지 → 이상 시점의 이력 만료 → 요청 재확인 불가 → 초기화 불가. 새로고침해도 IndexedDB의 미확인 요청은 남는다. 서버의 동일 요청 결과가 남아 있어도 UI에서 확인할 수 없다.

**확인 수준:** 임시 컴포넌트 검사에서 기존 요청의 재확인 버튼 비활성화, 이력 만료 후 대화상자 진입 비활성화 두 조건을 각각 재현했다. 실제로 30분 동안 응답 유실을 유지하는 E2E는 실행하지 않았다.

**개선:** 신규 발행과 기존 요청 결과 조회를 분리한다. `requestId`로 기존 결과만 확인하는 경로는 진단 이력의 유효성과 독립적으로 제공한다. 서버가 결과를 보관하지 않은 경우에는 결과 미확정 상태와 다음 행동을 명시한다. 현재 POST를 조건 없이 재호출하면 서버 기록 소실 시 신규 발행이 될 수 있으므로, 버튼의 `disabled`만 제거하는 수정은 충분하지 않다.

**완료 기준:** 응답 유실 후 이력 만료, 새로고침, 다른 설비 이동 이후에도 원래 requestId의 결과 조회가 가능하며 새 작업을 중복 발행하지 않는다.

## 2. P2 — 기본 범위가 5분 또는 15분이어도 최초 축소 버튼이 비활성화

**근거:** `apps/web/src/components/SignalWorkbench.tsx:111`, `:171`, `apps/web/src/routes/SettingsPage.tsx:221`.

설정에서 최근 5분을 저장하고 진단 화면에 들어오면, 30분 이력을 보유해도 `viewRange`는 `null`이다. 축소 버튼은 `disabled={noData || !viewRange}`이므로 비활성화된다. 사용자는 먼저 확대하거나 전체 구간으로 전환해야 한다. 실시간 추종 상태와 더 넓은 범위를 볼 수 있는 상태가 혼동되어 있다.

**확인 수준:** 표시 범위와 버튼 조건을 소스에서 대조했다. 임시 컴포넌트 검사는 5초 제한을 넘어 완료 판정에 사용하지 않았다.

**개선:** 축소 가능 여부를 현재 표시 구간의 길이와 보유 이력 길이로 계산한다. 추종 여부는 별도 상태로 둔다. 5분, 15분, 30분 각각에서 처음 진입했을 때와 추종 복귀 후의 버튼 상태를 확인한다.

## 3. P2 — 후속 업무 화면으로 이동하면 선택한 설비가 COATER-02로 바뀜

**근거:** `apps/web/src/App.tsx`의 `useSensorStream(true, … SELECTED_EQUIPMENT_ID)` 호출, `apps/web/src/hooks/useSensorStream.ts`의 `selectEquipment`, `apps/web/src/components/AppHeader.tsx`의 신호 분석 링크.

DRYER-02 진단에서 정비 관리로 이동하면 URL에 설비 ID가 없어 스트림 훅에 COATER-02가 전달된다. 훅은 전역 선택 설비도 COATER-02로 변경한다. 이후 헤더의 ‘신호 분석’은 방금 보던 건조기가 아닌 코터를 연다. 저장된 업무 기록 자체가 섞이는 문제는 아니지만, 진단과 후속 처리 사이의 맥락이 끊긴다.

**확인 수준:** 경로에 따른 상태 변경과 링크 생성 로직을 추적했다. 브라우저 왕복 재현은 미실시.

**개선:** 마지막으로 선택한 진단 설비와 개요용 스트림 구독 대상을 분리한다. 비진단 경로 진입이 사용자의 선택을 덮어쓰지 않도록 한다. DRYER-02 → 정비 관리 → 헤더 신호 분석 경로를 회귀 검사한다.

## 4. 디자인 — 정보 밀도와 핵심 행동의 위계 개선

공정 개요와 진단 화면을 로컬 브라우저에서 확인했다. 설비의 정상, 경고, 이상 상태를 색뿐 아니라 텍스트와 아이콘으로 구분한 점은 좋다. 다만 다음 개선 여지가 있다.

- **작은 글씨가 주요 판단 정보에도 사용된다.** 개요의 설비명, 상태, 시각과 진단의 근거, 설명 대부분이 10–12px다. `styles.css`의 `.flow-equipment-list--dense`, `.evidence-list`, `.incident-time`, `.analysis-disclaimer`, `signalChart.ts`의 축과 범례가 해당한다. 설비명, 핵심 근거와 행동 안내는 13–14px 수준으로 우선 확대하고, 덜 중요한 설명의 노출량을 줄이는 편이 낫다. 단순히 모든 글꼴을 키우면 현재 3열 구조가 더 조밀해진다.
- **진단의 권장 조치가 원인 후보와 근거 아래에 있다.** 1440×1024 캡처에서도 우측 하단의 권장 조치가 첫 화면 아래로 이어진다. 상단 ‘현장 검증’ 이동 링크가 있어 접근 불가 문제는 아니다. 다만 새 사용자가 점검 요청 동선을 빨리 이해하도록 우측 상단에 현재 업무 상태와 주 행동을 요약하거나, 우측 패널 안에서 행동 영역을 고정하는 방법을 검토할 수 있다.
- **기술 설명이 차트 도구 모음의 공간을 차지한다.** ‘보존/표시 시점 수’는 데이터 요약의 한계를 이해하는 데 도움이 되지만 `Canvas`, 수신 간격 같은 구현 정보는 상세 설명으로 옮길 수 있다. 도구 모음에서는 현재 범위, 추종 여부, 이상 구간 이동을 먼저 읽을 수 있게 한다.
- **모바일에서 차트까지의 거리가 길다.** 390×844 화면에서는 헤더, 설비 목록 버튼, 공정 단계, 이동 링크, 도구 모음과 설명을 지난 약 630px 지점부터 첫 차트가 나온다. 첫 화면에 장력 차트 하나와 다음 패널 제목 정도만 보인다. 모바일에서는 공정 단계를 접고, 상세 기술 설명을 펼침 영역으로 옮겨 설비 상태와 신호 비교를 더 일찍 보여주는 편이 좋다.

화면 밝기와 글꼴 크기에 대한 평가는 사용성 개선 의견이며, 접근성 표준 위반이나 색 대비 검사 통과 여부로 단정하지 않는다.

## 5. 접근성 — 차트의 범례와 값 탐색에 키보드 대안이 부족함

**근거:** `apps/web/src/components/SignalWorkbench.tsx`의 Canvas 차트 `role="img"`, `legendselectchanged`, `apps/web/src/lib/signalChart.ts`의 `legend`, `tooltip`.

확대, 이동 버튼과 이상 시점 참고값은 HTML로 제공되지만, 시리즈 숨기기와 임의 시점의 tooltip 탐색은 Canvas 상호작용에 의존한다. 이미지 역할과 차트 설명만으로 이 기능을 키보드나 스크린리더에 제공하지는 못한다.

**개선:** HTML 체크박스로 시리즈 표시를 조절하고, 선택 시점의 값을 읽을 수 있는 표 또는 시점 이동 컨트롤을 제공한다. 기존 일반 키보드 검사와 별개로 범례 및 시점 탐색의 동등 기능을 검증한다. 전 구간 원본 데이터 테이블을 한 번에 렌더링할 필요는 없다.

## 6. 최적화 — 비진단 화면의 수신과 차트 전체 갱신 줄이기

**근거:** `App.tsx`의 항상 활성화된 스트림, `useSensorStream.ts`의 500ms 배치, `operationsStore.ts:103`, `SignalWorkbench.tsx:108`.

설정, 알림, 정비 관리에서도 센서 메시지를 계속 수신한다. 배치마다 링 버퍼 전체를 새 배열로 복사하며, 진단 화면에서는 요약 시점과 모든 시리즈 데이터를 다시 만들고 `notMerge: true`로 전체 옵션을 설정한다. 점 개수 상한과 코드 분할은 이미 구현되어 있으므로, 무제한 데이터 증가나 무조건적인 성능 실패로 볼 문제는 아니다.

우선순위는 다음과 같다.

1. 개요와 진단에 필요한 구독을 구분하고 비진단 화면에서 보관 배열 갱신을 줄인다. 헤더의 연결 상태가 필요하면 가벼운 연결 확인과 센서 전체 수집을 분리한다.
2. 추가할 새 시점이 없는 배치는 배열 복사와 상태 발행을 생략한다.
3. 차트의 정적 축, 제목과 범례 설정을 데이터 갱신과 분리한다. 고정된 시리즈 ID와 데이터 부분 갱신을 적용할 때 설비별 패널 수 변경, 범례 선택과 확대 범위가 보존되는지 함께 검증한다.
4. 숨겨진 탭에서의 처리량과 화면 복귀 후 데이터 복구를 함께 설계한다.

현재 검토에서는 기존 벤치마크를 다시 측정하지 않았다. 개선 효과의 비율은 제시하지 않는다. 10만 시점 조건만이 아니라 기본 18,000시점, 비진단 메뉴, 숨겨진 탭에서 CPU와 할당량을 비교한 뒤 적용한다.

## 7. 코드 구조 — 화면별 책임과 스타일 경계 정리

라우트 지연 로딩, 서버 조회와 업무 저장의 분리, 설비 프로필을 통한 차트 재사용은 유지할 만하다. 프레임워크 교체나 대규모 재작성은 필요하지 않다.

- `styles.css`는 1,541줄로 개요, 진단, 업무 화면과 반응형 재정의를 함께 관리한다. 기본 선언 뒤 여러 미디어 쿼리와 후속 덮어쓰기가 배치되어 수정 영향 범위를 파악하기 어렵다. 공통 토큰과 셸을 남기고 화면 또는 기능별 스타일로 나눈다.
- `domain/workspace.ts`는 729줄에 상태 전이, 알림 생성, 설정, 검증과 저장 문서 형식을 함께 다룬다. 공개 command 진입점과 원자적 저장은 유지하면서 명령별 처리, 문서 검증과 notification policy를 분리하면 변경 범위가 명확해진다.
- `IncidentsPage.tsx` 523줄, `ProductionPage.tsx` 451줄, `MaintenancePage.tsx` 420줄이다. 같은 파일 안에 하위 컴포넌트도 있으므로 줄 수만으로 결함은 아니다. 목록 필터, 상세 표시, 편집 폼, 생산 집계 모델처럼 함께 바뀌는 단위부터 파일을 나누는 것이 유용하다.
- `Button`/`StatusBadge`와 별도의 `.workspace-button`/`StatusPill`이 공존한다. 밝은 업무 화면과 어두운 진단 화면의 차이는 테마와 variant로 표현하고, 키보드 초점, 비활성화와 크기 규칙은 공통화할 수 있다.

테스트 실행 중 파일 import와 브라우저 도구에도 큰 지연이 있었다. 따라서 시간 제한 초과를 곧바로 제품 기능 회귀로 단정할 수 없다. 반대로 이전 캐시가 성공했다고 현재 전체 테스트가 통과했다고 보고해서도 안 된다.

대용량 생성 검사는 일반 단위 검사와 스트레스 검증의 목적을 구분하고 해당 검사의 제한 시간을 명시하는 것이 좋다. UI 검사 실패는 여유 있는 실행 환경에서 개별 재현하고, 시간 제한을 일괄 늘리는 것으로 숨기지 않는다. 기존 테스트에는 ‘응답 유실 + 이력 만료’와 ‘기본 5분 범위의 최초 축소’ 조합을 추가할 가치가 있다.

## 권장 작업 순서

요청 결과 조회와 신규 발행 분리 → 차트 축소 조건과 설비 선택 유지 수정 → 차트 키보드 대안과 글자 크기/행동 위계 개선 → 비진단 구독과 차트 갱신 비용 측정 → 기능별 파일 분리.

인증, 실제 제조 장비 연동, 다중 기기 저장과 서버 영속 멱등성은 README에서 이미 미지원 범위를 밝히고 있어 이번 검토에서는 새로 발견한 오류로 세지 않았다.
