# 두 번째 설비의 진단 재사용 사례

2026년 8월 31일, `COATER-02` 전용 화면을 공통 진단 구성으로 분리하고 `DRYER-02`를 같은 API, 스트림, 차트, 점검 처리 흐름에 연결했다. 두 번째 설비 이름만 표시하는 목업이 아니라 실제 이력 조회와 구독 대상, 안전 확인, 발행 기록이 바뀐다. 두 번째 고객사나 실제 현장에 적용한 사례는 아니다.

## 달라지는 구성과 공통 구현

| 항목 | COATER-02 | DRYER-02 |
| --- | --- | --- |
| 합성 이상 | 웹 장력과 코팅 품질 이상 | 건조로 온도 편차 |
| 이력 경로 | `/api/equipment/COATER-02/history` | `/api/equipment/DRYER-02/history` |
| WebSocket 구독 | `/stream` 기본값 | `/stream?equipmentId=DRYER-02` |
| 표시 센서 | 좌우 장력, 온도, 속도, 결함률 | 온도, 속도, 후단 결함률 |
| 패널 / 시리즈 | 4 / 6, 설정값 포함 | 3 / 4, 설정값 포함 |
| 합성 온도 설정값 | 160°C | 165°C |
| 첫 번째 안전 확인 | 댄서 롤 가드와 작업 동선 | 고온부에 접근하지 않는 외부 계기 점검 |
| 시나리오상 점검 시간 | 90초 | 120초 |

온도 설정값과 점검 시간은 데모 구성값이다. 실제 현장의 운전 기준이나 표준 작업 시간을 제안하는 값이 아니다.

- [진단 프로필](../apps/web/src/domain/diagnosticProfiles.ts): 표시할 센서, 단위, 축 범위, 설정값, 이벤트와 안전 안내를 선언한다.
- [공통 차트 옵션](../apps/web/src/lib/signalChart.ts): 패널 수에 따라 축과 범례, 기준선을 생성한다. [SignalWorkbench](../apps/web/src/components/SignalWorkbench.tsx)는 인스턴스 수명, 확대/이동, 실시간 갱신과 원본 참고값을 함께 관리한다.
- [공유 계약](../packages/contracts/src/index.ts): 지원 설비 ID와 설비별 안전 체크리스트의 기준이다. 서버도 같은 체크리스트를 검사한다.
- [서버 런타임](../apps/stream-server/src/runtime.ts): 설비별 합성 이력과 WebSocket 구독을 처리하고 발행 요청의 이상 ID를 확인한다.
- [공통 진단 페이지](../apps/web/src/routes/DiagnosticsPage.tsx), [발행 다이얼로그](../apps/web/src/components/VerificationDialog.tsx), [업무 명령](../apps/web/src/domain/workspace.ts): 두 설비가 같은 구현을 사용한다. 정비 관리와 이상 종결 화면을 복제하지 않았다.

## 전환 시 잘못된 설비를 판단하지 않도록 한 처리

1. 설비 선택이 바뀌면 기존 링 버퍼, 시퀀스, 연결 상태와 발행 결과 표시를 초기화한다. 화면의 이력 Query 키에도 설비 ID를 포함한다.
2. REST 응답의 `equipmentId`가 요청 대상과 다르면 성공으로 채택하지 않는다. 이전 설비의 늦은 응답이나 프레임은 스토어에서도 거부한다.
3. 기존 소켓을 정리하고 새 구독을 맺는다. `hello`와 `sensor.point`의 설비 ID가 구독 대상과 다르면 연결을 닫고 재연결한다.
4. 주석은 이상 ID로 구분한다. 작업 발행 결과는 현재 설비에 해당하는 저장 기록으로 복원한다.
5. 결과를 확인하지 못한 발행 요청이 다른 설비에 남아 있으면 새 발행을 막고 원래 설비의 재확인 경로를 안내한다. 새 요청으로 덮어쓰지 않는다.

## 검증 근거

- [E2E 재사용 검사](../apps/web/e2e/equipment-reuse.spec.ts): 실제 HTTP와 WebSocket의 설비 전환, 새로고침, 건조기 안전 조건, 작업 발행과 점검 완료, 다른 설비의 결과 혼입 방지, 미확인 요청의 동일 본문 재시도를 검사한다.
- [스토어 검사](../apps/web/src/store/operationsStore.test.ts): 전환 이후 이전 설비의 이력과 센서 데이터, 연결 상태가 현재 데이터를 덮어쓰지 않는지 확인한다.
- [API 검사](../apps/web/src/api/client.test.ts), [서버 검사](../apps/stream-server/src/runtime.test.ts): 이력 ID 불일치와 설비에 맞지 않는 안전 체크리스트를 거부한다.
- [차트 검사](../apps/web/src/components/SignalWorkbench.test.tsx): 건조기의 3개 패널, 4개 시리즈와 165°C 설정값, 장력 패널 제외를 검사한다.
- [반응형 검사](../apps/web/e2e/responsive-layout.spec.ts), [접근성 검사](../apps/web/e2e/ux-recovery.spec.ts): 두 진단 구성을 모두 대상으로 한다. 자동 검사이며 실기기나 전체 화면의 육안 검수와 같지 않다.

최신 실행 결과는 [제출 준비 기록](./SUBMISSION_REVIEW_2026-08-31.md), 실제 화면 갱신 계측은 [성능 문서](./PERFORMANCE.md)를 따른다.

## 재사용 범위와 남은 비용

현재 재사용 단위는 **같은 코팅 라인 신호 어휘를 쓰는 두 합성 진단 구성**이다. 두 응답 모두 기존 `SensorPoint`의 다섯 필드를 전송하며 건조기 화면은 그중 세 필드를 표시한다. 임의 태그 스키마, 단위 자동 변환, 설비별 수집 주기 또는 벤더 프로토콜을 동적으로 지원하지 않는다. 합성 시나리오는 서로 독립적이며 라인 전체의 물리적 인과관계를 계산하는 시뮬레이터도 아니다.

비슷한 세 번째 설비를 추가하려면 지원 ID와 안전 계약, 합성 데이터/이상 구성, 진단 프로필과 회귀 검사를 추가해야 한다. 완전히 다른 센서 집합이라면 `SensorPoint`, 검증기와 샘플러의 센서 키도 확장해야 한다. 프론트엔드 설정 한 줄만으로 모든 설비를 연결할 수 있다고 설명하지 않는다.

이번 확장에서 처음 필요한 공통화를 수행했으므로 개발 시간이 얼마나 줄었는지는 측정하지 않았다. 근거는 같은 페이지와 차트, 상태 전이 구현으로 서로 다른 구성을 실행하고 전환 안전성을 검증했다는 점이다.
