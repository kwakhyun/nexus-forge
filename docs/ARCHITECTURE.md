# 아키텍처

## 구성

```text
브라우저
  ├─ React 운영 화면
  ├─ TanStack Query ─ REST ─ stream-server ─ 합성 설비/센서/생산 실적
  ├─ operationsStore + RingBuffer ─ WebSocket ─ stream-server
  └─ workspaceStore ─ 검증된 업무 명령 ─ IndexedDB
                                            └─ 같은 브라우저 탭 간 변경 알림
```

```text
apps/
  web/             운영 화면, 차트, 테스트, Storybook
  stream-server/   REST API, WebSocket, 결정론적 센서 시뮬레이션
packages/
  contracts/       API와 스트림의 공유 TypeScript 계약
  ui/              토큰과 재사용 UI 프리미티브
```

Turborepo가 패키지 빌드 순서와 캐시를 관리합니다. 웹과 서버는 `@nexus/contracts`를 공유하므로 센서 또는 작업 지시 스키마가 달라질 때 컴파일 단계에서 불일치를 확인할 수 있습니다.

## 상태 경계

- TanStack Query: 공정 요약, 30분 센서 이력, 14일 합성 생산 실적, 작업 지시 생성의 비동기 상태
- `operationsStore` (Zustand): 구독 설비 ID와 마지막 진단 설비 ID, 스트림 연결, 고빈도 센서 스냅샷, 역할 선택, 다이얼로그와 이상 ID별 탭 내 주석
- `workspaceStore` (Zustand): IndexedDB 문서의 읽기 모델, 저장 상태, 업무 명령 전달. 미확인 요청과 발행 결과는 기존 진단 UI에 동기화
- IndexedDB: 작업, 이상 처리, 알림, 설정, 결과 미확인 발행 요청. 저장된 업무 데이터의 기준
- `workspaceDraftStore` (Zustand): 저장 전 담당자, 결과, 종결 사유와 설정 입력. 현재 탭의 화면 이동 중 유지하되 새로고침과 다른 탭에는 공유하지 않음
- URL: 이상과 작업의 선택 ID. 목록 필터에 맞지 않게 상태가 바뀌어도 상세 기록을 유지
- 컴포넌트 로컬 상태: 검색 필터, 차트에서 고정한 구간과 범례 선택

이 구분으로 서버 캐시와 프레젠테이션 상태가 섞이지 않으며, 스트림 갱신이 불필요한 전체 화면 렌더링으로 퍼지는 것을 줄였습니다.

## 데이터 흐름

1. 진단 URL에서 지원 설비 COATER-02 또는 DRYER-02를 선택하고 설비 ID를 포함한 Query 키로 최근 30분 이력을 가져옵니다. 공개 데모 기본값은 18,000개이며 성능 검증 경로는 최대 100,000개를 허용합니다. 응답 ID가 요청 대상과 다르면 거부합니다.
2. 최근 30분의 입력이 20,000개를 넘으면 전체 시간 범위의 경계와 센서별 극값을 보존해 먼저 줄입니다. 요청 중 수신한 최신 시점과 합쳐 최대 20,000개 링 버퍼에 넣고 중복 및 과거 스트림 프레임을 제외합니다.
3. WebSocket은 구독한 설비의 새 시점과 설비 ID를 250ms 간격으로 전송합니다. 설비를 바꾸면 이전 소켓, 배치와 버퍼를 정리하고 새 대상을 구독합니다. 늦은 이전 설비의 이력, 프레임과 연결 상태는 현재 스토어에 반영하지 않습니다.
4. 클라이언트는 수신값을 500ms 단위로 모아 한 번에 상태에 반영합니다. 새 시점이 없는 배치는 배열 복사와 상태 발행을 생략합니다. 구독은 개요와 지원 진단 경로에서만 활성화하고, 숨겨진 탭에서는 소켓과 타이머를 정리합니다. 진단 화면 복귀 때 이력을 재조회합니다. 마지막 진단 설비는 개요의 구독 대상과 분리해 후속 업무에서 돌아와도 유지합니다.
5. 원본을 150개 공통 구간으로 나눠 각 구간의 양 끝과 다섯 센서별 최솟값/최댓값의 시점을 합칩니다. 중복을 제거한 출력은 최대 1,800개 시점이며, 입력이 예산 이내이면 그대로 사용합니다.
6. ECharts Canvas 렌더러가 진단 프로필에 선언한 패널을 그립니다. COATER-02는 4개 패널/5개 신호와 설정값, DRYER-02는 3개 패널/3개 신호와 설정값입니다. 모든 시리즈의 `sampling`을 `none`으로 지정해 공통 시점을 다시 센서별로 축소하지 않습니다.
   패널, 화면 크기, 시간대 또는 범례 선택이 바뀌면 전체 옵션을 구성합니다. 일반 수신 배치는 고정된 시리즈 ID의 데이터와 표시 범위만 갱신합니다. HTML 체크박스와 시점 슬라이더, 한 시점의 센서값 표를 Canvas의 키보드 대안으로 제공합니다.
7. 이상 발생 시점의 참고값은 차트 표시용 요약이 아닌 보존 버퍼에서 찾습니다. 기본 18,000개 이력에서는 원본 시점이며, 20,000개를 넘는 고밀도 입력에서는 1차 극값 요약을 거친 시점입니다. 해당 시점의 데이터가 없으면 임의의 인접 값을 근거로 표시하지 않습니다.

보존하는 것은 공통 구간별 센서 극값과 경계입니다. 같은 센서의 작은 국소 피크, 반복 횟수, 지속 시간까지 보존하지 않습니다. 확대는 요약된 시리즈를 확대하며 원본 구간을 다시 샘플링하지 않습니다. 보존 시점 수와 표시 시점 수, 해석 한계를 차트에 함께 표시합니다. 초기 변화량 기반 방식에서 바꾼 이유와 반례는 [기술 판단 사례](./ENGINEERING_CASE_STUDIES.md)에 있습니다.

### 설비 재사용 경계

`diagnosticProfiles.ts`의 패널, 기준값, 이벤트와 안내를 공통 페이지, 차트와 원인 레일에 전달합니다. 안전 체크리스트는 서버와 웹이 공유하는 계약으로 관리합니다. 두 설비 모두 기존 다섯 필드의 `SensorPoint`를 사용하므로 임의의 다른 센서 스키마까지 지원한 것은 아닙니다. 변경 지점, 전환 보호와 시험 근거는 [설비 재사용 사례](./EQUIPMENT_REUSE.md)에 정리했습니다.

### 전체 흐름 성능 계측

`VITE_PERFORMANCE_PROBE=true`인 로컬 벤치마크 빌드에서만 수신, 배치, 이력 채택, 차트 완료와 발행 저장 시점을 기록합니다. 한 번에 최대 3,000개를 담고 장시간 실행에서는 주기적으로 회수해 계측기 자체의 누적을 제한합니다. 외부로 전송하지 않으며 일반 빌드는 계측 객체와 관찰자를 만들지 않습니다. [실제 앱 측정기](../scripts/benchmark-application.mjs)는 앱에 설치된 Vite 버전과 공통 서버 런타임을 사용하며, 화면 합성의 실측이 아닌 렌더 프레임 기회를 측정합니다. 세부 정의와 원본은 [성능 문서](./PERFORMANCE.md)를 따릅니다.

## 업무 기록의 데이터 흐름

1. `WorkspaceBootstrap`이 IndexedDB를 열고 저장 기록의 버전과 참조, 상태 형식을 검증합니다. 처음 방문하면 두 설비의 현재 합성 이상과 명시적인 완료 예시 두 건을 추가합니다. 기존에 저장한 같은 이상은 덮어쓰지 않습니다.
2. 폼과 버튼은 명령을 전송합니다. `applyWorkspaceCommand`는 허용된 상태 전이와 필수 기록을 검사하는 순수 함수입니다.
3. 하나의 IndexedDB `readwrite` 트랜잭션 안에서 최신 문서 읽기 → 명령 적용 → 문서 쓰기를 처리합니다. 여러 탭이 서로 다른 필드를 수정해도 이전 스냅샷 전체를 덮어쓰지 않습니다.
4. 트랜잭션 완료 후에만 UI 상태와 성공 메시지를 갱신합니다. 변경 사실은 BroadcastChannel로 알리고, 다른 탭은 DB의 최신 버전을 읽습니다. 포커스 복귀 시에도 갱신합니다.
5. 현장 검증 발행은 미확인 요청을 먼저 저장하고 서버를 호출합니다. 성공 응답을 작업, 이상 상태, 알림과 함께 저장하면서 미확인 요청을 해제합니다. 이 최종 저장이 실패하면 성공으로 안내하지 않습니다. 다른 설비의 미확인 요청이 남아 있으면 새 발행을 막고 원래 요청의 복구를 안내합니다. 확정된 결과는 선택한 설비에 맞춰 복원합니다.
6. 정비 작업은 대기 → 진행 중 → 완료, 이상은 미확인 → 확인됨 → 조치 중 → 종결입니다. 진단에서 바로 발행하면 별도의 확인 버튼 없이 조치 중으로 이동할 수 있습니다. 점검 완료 후 잔여 위험과 사유를 검토해야 별도로 종결됩니다.
7. 설정은 편집한 필드와 편집 시작값을 보냅니다. 최신 문서의 다른 필드는 유지하고 같은 필드가 달라졌으면 충돌로 처리합니다. 담당자 변경에도 시작값 비교를 적용합니다. 외부 변경 때문에 폼을 강제 재마운트하지 않습니다.
8. 다른 탭에서 작업을 완료하거나 기록을 초기화해도 현재 탭의 초안을 자동 삭제하지 않습니다. `WorkspaceDraftsNotice`에서 저장 전 내용을 확인하고 개별적으로 지울 수 있습니다. 기록이 읽기 전용으로 바뀌면 추가 입력과 저장을 막되 초안은 별도로 남깁니다.

같은 합성 이상 ID는 처음 보관한 발생 시각과 업무 이력을 유지합니다. 서버 시뮬레이터 재시작으로 기준 시각이 바뀌어도 저장한 사건의 시각을 뒤로 이동시키지 않습니다. 따라서 진단의 현재 합성 시나리오 시각과 저장 기록 시각은 재시작 후 다를 수 있습니다.

센서 시점 20,000개를 매번 영속 저장하지 않습니다. 업무 변경과 설정만 작은 버전 문서로 보관합니다. 작업은 예시 포함 최대 100건, 이상은 최대 100건, 알림은 최근 200건, 각 객체의 활동은 최근 100건입니다. 저장 문서 버전은 1이며, 알 수 없는 버전이나 손상 문서는 자동 덮어쓰기 대신 오류와 명시적 초기화 경로를 제공합니다. JSON 내보내기는 열람용이며 가져오기 기능은 없습니다.

같은 출처의 브라우저 탭 사이에서만 상태를 공유합니다. BroadcastChannel을 사용할 수 없으면 포커스 복귀 시 갱신합니다. IndexedDB는 서버 백업이 아니며 사이트 데이터 삭제, 비공개 세션 종료나 저장 공간 정리로 사라질 수 있습니다.

## 생산 분석과 처리 실적의 경계

`/api/production`은 완료된 시간대의 14일 합성 코팅 실적을 생성합니다. 최근 24시간/7일을 이전 동기간과 비교하고, 불량 판정 비율은 전체 검사 길이를 분모로 합산합니다. 날짜별 달력 집계가 아닌 24시간 구간 집계임을 화면에 표시합니다. 합성 실적에는 사용자 작업 완료를 생산 효과로 반영하지 않습니다. 브라우저의 점검 완료와 이상 종결 건수는 별도 영역에서 집계하고 초기 예시 이력은 제외합니다.

## 장애 대응

- 스트림 종료 시 지수 백오프로 최대 10초 간격까지 재연결합니다.
- 소켓 연결 여부와 센서 신선도를 분리합니다. 센서 값이 5초 넘게 끊기면 지연 상태로 전환하고, 하트비트를 포함한 전체 프레임이 35초 넘게 끊기면 연결을 강제로 다시 맺습니다.
- 수신 대기, 연결 중, 센서 지연, 재연결 중, 오프라인, 정상 상태를 헤더에 명시합니다.
- 공정 요약의 첫 조회 실패는 탐색과 재시도가 가능한 오류 화면으로 전환합니다. 이후 갱신 실패는 마지막 화면과 경고를 함께 유지합니다.
- REST 요청은 10초 타임아웃과 취소 신호, 응답 형식 검증을 적용합니다. 렌더링 예외와 비동기 화면 로딩 실패에는 오류 경계를 제공합니다.
- 30분 이력 실패는 차트 안에서 재시도합니다. 이력 부재, 센서 지연, 현황 갱신 실패 동안 신뢰도를 숨기며 현장 검증 발행을 차단합니다. 가동 중 점검이 허용되지 않은 인시던트도 발행을 보류합니다.
- 현장 검증은 발행 중 입력과 모달 닫기를 잠그고, 응답이 유실되면 저장한 요청 ID로 읽기 전용 결과 조회를 실행합니다. 이력 만료는 신규 발행만 막으며 기존 요청 조회를 막지 않습니다. 결과가 없으면 미확정 상태로 남기고, 사용자의 명시적 추적 종료 시 요청 ID를 대조한 뒤 활동 이력을 남깁니다. 미확인 요청과 발행 결과는 새로고침 후 복원합니다. 주석과 저장 전 폼 입력은 탭 메모리이며 새로고침 시 초기화됩니다. 미완료 DB 쓰기나 미저장 폼이 있으면 이탈 경고를 요청합니다.
- 저장소 연결과 트랜잭션에 5초 제한을 두고 접근 거부, 공간 부족과 손상 기록을 안내합니다. 결과 미확인 요청이 있으면 DB 트랜잭션에서도 초기화를 거부해 다른 탭의 오래된 화면으로 삭제할 수 없게 합니다.
- `VITE_SENTRY_DSN`이 있을 때만 Sentry를 동적으로 로드합니다.

## 공개 데모 배포 경계

Vercel의 Production target을 공개 데모의 배포 환경으로 사용합니다. `dist/client`의 정적 자산은 CDN으로 제공하고, REST API와 WebSocket 스트림은 동일 저장소의 Vercel Functions로 배포합니다. Functions와 로컬 Node 서버는 같은 요청 처리 및 센서 시뮬레이션 모듈을 사용하므로 실행 환경에 따른 계약 차이를 줄였습니다. 이 구성은 실제 제조 고객사의 상용 운영 환경을 의미하지 않습니다.

Vercel의 Git 푸시 직접 배포는 `vercel.json`에서 끕니다. `main`에 푸시하면 GitHub Actions가 lint, typecheck, 단위 및 컴포넌트 테스트, 빌드, Storybook과 Chromium E2E를 병렬 검증합니다. 두 작업이 모두 성공한 뒤에만 암호화된 Vercel 배포 훅을 호출합니다. 배포가 끝나면 공개 `/api/health`의 `release`가 해당 GitHub 커밋 SHA와 일치하는지 확인하고, UI 셸, 공정 요약, 센서 이력, WebSocket 수신까지 스모크 테스트합니다. 빌드 성공과 공개 승격 사이의 검증 순서를 명시적으로 고정한 구성입니다.

클라이언트는 Functions 재시작과 배포 교체에 대비해 WebSocket 연결을 지수 백오프로 다시 맺습니다. 서버의 발행 기록은 런타임 메모리에, 사용자 후속 처리는 브라우저 IndexedDB에 보관됩니다. 서버가 브라우저의 진행/완료 상태를 관리하거나 다른 기기에 전달하지 않습니다. 실제 다중 사용자 운영에는 인증과 관계형 데이터베이스 등의 영속 저장소가 필요합니다.

요청 ID 기반 중복 방지는 기록이 남아 있는 단일 인스턴스에 한정됩니다. 분산 환경의 exactly-once 보장은 없으며, UI의 중복 클릭 방지와 서버의 영속 멱등성은 구분합니다.

로컬 통합 서버의 `/health`는 같은 프로세스에 연결된 WebSocket 클라이언트 수를 반환합니다. Vercel에서는 REST와 스트림 Function의 인스턴스가 분리되고 전역 접속 상태 저장소가 없으므로 `clients: null`과 `clientCountScope: "unavailable"`을 반환해 `0명 접속`으로 오해하지 않도록 했습니다.

ChatGPT Sites용 정적 산출물은 보조 배포 호환성을 위해 계속 생성합니다. 실제 온프레미스 환경에서는 리버스 프록시가 `/api`와 `/stream`을 같은 출처로 노출하는 구조가 적합합니다.

## 기능별 파일 경계

- `domain/workspace.ts`는 공개 타입과 명령 진입점을 유지합니다. `domain/workspace/`의 모델, 문서 검증, 시드, 알림 정책과 업무별 명령 처리기가 책임을 나눕니다. IndexedDB 원자적 저장과 v1 문서 형식은 유지합니다.
- `components/operations/`는 이상 상세, 작업 상세와 생산 그래프를 담당합니다. `domain/production.ts`는 화면에서 분리한 생산 집계 모델을 제공합니다.
- `styles.css`는 `styles/`의 기본, 헤더, 진단, 개요, 상태 안내, 반응형, 업무 화면과 접근성 스타일을 순서대로 가져옵니다. 기존 캐스케이드 순서를 유지합니다.
- `packages/ui`의 Button은 밝은/어두운 테마와 위험 행동 variant를, StatusBadge는 pill 표시와 업무용 tone을 지원합니다. 업무 화면도 공통 초점과 비활성화 규칙을 사용합니다.

브라우저 회귀 검사는 서버를 빌드해 실행하고 웹의 production preview를 사용합니다. 개발 서버의 최초 모듈 변환 지연을 테스트 대상에 섞지 않으며, API와 WebSocket은 같은 로컬 서버로 프록시합니다.
