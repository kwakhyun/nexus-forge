# 기술 결정 기록

이 문서는 NEXUS Forge의 주요 기술 선택이 어떤 문제와 대안에서 나왔는지 기록합니다. 현재 공개 데모 범위에서 내린 결정이며, 실제 설비 규모와 운영 조건이 달라지면 아래의 재검토 조건에 따라 바꿉니다.

## 결정 원칙

1. 작업자가 이상을 발견하고 다음 행동을 결정하는 시간을 줄이는가?
2. 고빈도 데이터가 React 렌더링과 브라우저 메모리를 통제 불가능하게 만들지 않는가?
3. 공개 데모의 기술 범위와 실제 상용 운영의 차이를 설명할 수 있는가?
4. 다음 현장에서도 계약과 컴포넌트를 재사용할 수 있는가?

## 주요 결정

| 결정 | 선택한 이유 | 검토한 대안 | 감수한 비용 | 다시 검토할 조건 |
| --- | --- | --- | --- | --- |
| 일반 KPI 현황판보다 이상 진단과 현장 검증 흐름을 우선 | 정보량보다 이상 원인 파악과 다음 행동이 제조 운영자의 판단에 직접 연결됨 | 생산량과 OEE 중심 대시보드 | 정상 운영의 폭넓은 지표를 첫 범위에서 제외 | 실제 사용자가 진단보다 전체 생산 계획을 우선 요구할 때 |
| REST와 WebSocket 역할 분리 | 이력과 작업은 요청 수명주기가 있고 센서 값은 연속적으로 도착함 | REST 폴링, SSE 단독 | 연결 상태, 재연결, 느린 클라이언트 처리가 필요 | 단방향 알림만 필요하거나 중간 메시지 계층을 도입할 때 |
| TanStack Query와 Zustand 상태 분리 | 서버 캐시와 고빈도 스트림/UI 상태의 갱신 규칙이 다름 | 단일 전역 스토어, Query 캐시에 스트림 직접 기록 | 상태 경계를 학습하고 유지해야 함 | 스트림이 서버 집계값 중심으로 바뀌어 갱신 빈도가 낮아질 때 |
| 역할별 작업 지시 입력 분리 | 라인 엔지니어는 안전 확인 후 즉시 발행하고, 교대 관리자는 담당자를 선택해 위임해야 함 | 두 역할에 동일한 담당자 선택 UI 제공 | 역할 조건에 따른 UI와 테스트 분기가 늘어남 | 서버 권한과 승인 절차를 도입해 화면 전환만으로 역할을 바꿀 수 없게 될 때 |
| 250ms 수신과 500ms 화면 반영 분리 | 패킷을 잃지 않으면서 React 상태 기록과 차트 갱신 횟수를 제한 | 패킷마다 상태 반영 | 최장 약 500ms의 표시 지연 | 즉각 제어처럼 지연 허용치가 더 낮은 화면을 만들 때 |
| 여러 센서를 함께 선택하는 변화량 기반 다운샘플링 | 센서별로 다른 시점을 선택해 상관관계가 왜곡되는 것을 피하고 짧은 이상값을 보존 | 단순 간격 샘플링, 센서별 LTTB, 서버 집계 | 휴리스틱 가중치를 도메인에 맞게 관리해야 함 | 실제 태그 범위와 중요도를 학습하거나 서버 멀티해상도 집계를 제공할 때 |
| ECharts Core와 Canvas 렌더러 | 다중 축, MarkArea, DataZoom을 제공하면서 많은 시점을 Canvas로 처리할 수 있음 | SVG 차트, D3 직접 구현, WebGL | 세밀한 번들 구성과 명령형 차트 수명주기 관리가 필요 | 시점 수가 Canvas 한계를 넘거나 3D/공간 시각화가 핵심이 될 때 |
| Vercel Functions와 로컬 서버가 런타임 공유 | 공개 데모와 로컬 개발에서 같은 REST, 스트림 계약을 검증할 수 있음 | 프론트엔드만 정적 배포, 별도 장기 실행 서버 | 메모리 영속성과 장기 연결 확장에 제약 | 실제 운영 환경, 다중 인스턴스 저장소, 메시지 브로커가 필요할 때 |
| 센서 신선도와 소켓 연결 상태 분리 | 열린 연결이나 하트비트만으로 실제 센서 수신을 정상으로 오인하지 않기 위함 | 소켓 `open`만 표시, 단일 타임아웃 | 상태와 타이머 테스트가 늘어나며 현장별 허용 지연을 조정해야 함 | 태그별 주기와 품질 정책을 서버 계약으로 제공할 때 |
| 이력 검증 실패 시 분석과 작업 발행 차단 | 불완전한 시계열로 높은 신뢰도와 조치를 제시하는 것이 현장 판단에 더 위험함 | 경고만 표시하고 기존 분석 유지 | 일시 장애 중 작업 흐름이 중단됨 | 검증된 캐시, 데이터 품질 점수와 부분 분석 정책을 도입할 때 |
| CI 성공 뒤 배포 훅으로 공개 빌드 시작 | Vercel 빌드가 GitHub E2E보다 먼저 공개 주소에 연결되는 경합을 제거하고 실제 공개 커밋까지 확인하기 위함 | Git 푸시 직접 배포, 수동 승격, 계정 기능인 Deployment Checks | 배포 시간이 늘고 배포 훅 비밀 관리가 필요 | Vercel Deployment Checks를 프로젝트에서 사용할 수 있거나 별도 릴리스 플랫폼을 도입할 때 |
| 3D 디지털 트윈 제외 | 원인 분석과 현장 작업 발행이라는 핵심 가치 검증보다 구현 비용이 큼 | Three.js 공장 레이아웃 | 공간 맥락을 보여주지 못함 | 설비 위치와 이동 경로가 판단의 핵심 정보가 될 때 |

## AI 협업과 검증 기준

공개 자료 조사, 디자인 대안, 구현 보조와 검토에 AI 도구를 사용했습니다. AI가 제안한 내용은 다음 조건을 통과해야 저장소의 결정으로 채택했습니다.

- 공개 자료 또는 저장소 코드로 사실을 확인할 수 있어야 합니다.
- TypeScript 계약, 단위 테스트 또는 E2E 사용자 흐름으로 동작을 재현할 수 있어야 합니다.
- 실제 제조 고객사 운영 경험이나 측정하지 않은 성과로 확대해서 표현하지 않습니다.
- 브라우저에서 문구, 반응형 레이아웃, 오류 로그와 핵심 행동을 다시 확인합니다.

## 기록 범위

이 기록은 완성된 선택을 사후에 나열하기 위한 문서가 아니라 면접과 후속 개발에서 선택의 전제와 한계를 검토하기 위한 기준입니다. 실제 사용자 인터뷰, 현장 네트워크, 장비 프로토콜과 운영 SLA는 공개 데모 범위에 포함되지 않습니다.
