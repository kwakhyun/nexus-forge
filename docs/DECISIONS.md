# 기술 결정 기록

이 문서는 NEXUS Forge의 주요 기술 선택이 어떤 문제와 대안에서 나왔는지 기록합니다. 현재 공개 데모 범위에서 내린 결정이며, 실제 설비 규모와 운영 조건이 달라지면 아래의 재검토 조건에 따라 바꿉니다.

## 결정 원칙

1. 작업자가 이상을 발견하고 다음 행동을 결정하는 시간을 줄이는가?
2. 고빈도 데이터가 React 렌더링과 브라우저 메모리를 통제 불가능하게 만들지 않는가?
3. 공개 데모의 기술 범위와 실제 상용 운영의 차이를 설명할 수 있는가?
4. 다음 현장에서도 계약과 컴포넌트를 재사용할 수 있는가?

## 2026년 8월 31일 UI/UX 보강

- 차트 수치 오버레이를 차트 아래의 원본 참고값으로 분리했습니다. 작은 화면에서 그래프를 가리지 않고, 실시간 값과 이상 발생 시점 값을 구별하기 위한 선택입니다.
- 제한된 화면 높이에 내용을 강제로 맞추지 않고 각 진단 영역을 스크롤 가능하게 했습니다. 모바일에는 영역 이동 링크를 추가해 현장 검증까지의 이동 거리를 줄였습니다.
- 당시에는 작업 지시 요청 ID와 체험 결과를 탭 메모리에 유지했습니다. 이후 아래의 운영 기능 확장에서 IndexedDB로 옮겨 새로고침 복원을 지원합니다. 서버의 분산 영속성으로 확대해 설명하지 않습니다.
- 센서 보관 기간을 개수뿐 아니라 30분으로 제한합니다. 이력과 실시간의 수집 주기가 다르기 때문에 개수 제한만으로는 화면에 표시한 시간 범위를 보장할 수 없습니다.
- 공정 현황, 센서 이력, 작업 지시의 런타임 응답 검증을 추가했습니다. TypeScript만으로 실제 네트워크 응답을 보장할 수 없기 때문입니다.

## 2026년 8월 31일 운영 기능 확장

| 결정 | 이유와 대안 | 비용과 재검토 조건 |
| --- | --- | --- |
| 다섯 메뉴를 같은 업무 흐름으로 연결 | 독립된 목업보다 이상 확인 → 진단 → 점검 → 종결의 실제 상태 변화가 필요. 넓은 MES/CMMS 전체 구현은 제외 | 최초 한 개, 이후 두 개 합성 진단 시나리오로 확장. 실제 생산 계획과 예방 정비가 필요하면 별도 도메인과 계약 확장 |
| IndexedDB의 원자적 read-modify-write | 외부 계정이나 DB 비용 없이 새로고침 복원과 같은 브라우저 탭의 변경 보존이 필요. localStorage 전체 문서 덮어쓰기는 탭 간 동시 변경을 잃을 수 있음 | 데이터는 해당 출처/브라우저에만 존재. 다중 사용자, 권한, 백업 요구가 생기면 서버 트랜잭션으로 이전 |
| 전송 전에 미확인 요청을 먼저 저장 | 서버 처리 후 응답 유실 또는 브라우저 종료 시 새 요청을 만들어 중복 시도하는 일을 줄임 | 브라우저의 요청 보존일 뿐 서버 exactly-once 보장은 아님. 외부 시스템 실행에는 서버 고유 키와 내구성 있는 저장소 필수 |
| 점검 완료와 이상 종결 분리 | 작업자가 점검했다는 사실만으로 이상 원인이 해소되었다고 확정할 수 없음. 결과 기록과 잔여 위험 확인을 별도 단계로 구성 | 한 단계가 늘어남. 실제 업무에는 역할별 승인과 서버 감사 로그 추가 필요 |
| 코팅 길이 기준의 생산 집계 | 코팅 공정 데모를 완성 셀 개수로 오인하지 않도록 단위를 m로 고정. 불량 길이 합계/검사 길이 합계로 계산 | 실제 라인 정의, 재작업/폐기 정책과 설비 정지 분류 검증 전에는 OEE나 현장 실적 지표로 사용 불가 |
| 합성 생산값과 사용자의 처리 실적 분리 | 점검 완료를 클릭했다는 이유로 수율이나 생산량이 개선된 것처럼 보이면 근거 없는 성과 표현이 됨 | 실제 효과 분석에는 실측 시계열, 작업 이력, 생산 Lot와 교란 요인 분석이 필요 |

IndexedDB의 트랜잭션 수명과 오류/완료 이벤트는 [MDN 사용 안내](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB)와 [IDBTransaction 문서](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction)를 기준으로 검토했습니다. 네트워크 요청은 DB 트랜잭션 밖에서 처리하고, 관련 업무 기록 변경만 하나의 트랜잭션에 둡니다.

## 운영 화면 재검토에서 보강한 결정

- **목록 조건과 선택 기록 분리:** 상태 변경 직후 기록이 필터에서 빠지더라도 상세와 성공 안내를 유지합니다. 선택 ID는 URL에 두고 필터 밖으로 이동했다는 안내를 표시합니다. 모바일에서는 명시적으로 고른 상세와 목록 사이의 포커스 및 스크롤을 관리합니다.
- **작성 중인 입력과 저장된 문서 분리:** 화면을 이동할 때마다 입력을 버리거나 저장된 문서를 즉시 바꾸지 않도록 탭 전용 초안 스토어를 둡니다. 다른 탭에서 작업을 완료해도 초안을 삭제하지 않고 별도의 확인/삭제 경로를 제공합니다. 새로고침까지 영속 저장하지 않으며 저장/취소와 이탈 경고로 범위를 알립니다. 장기 초안 복원이 필요해지면 별도 보관 정책과 명시적 복원 UI가 필요합니다.
- **설정의 필드 단위 변경과 충돌 확인:** 트랜잭션만으로는 오래된 폼 전체의 덮어쓰기를 막을 수 없습니다. 사용자가 수정한 필드와 시작값을 함께 보내 독립 필드는 병합하고 같은 필드의 외부 변경은 거부합니다. 담당자도 같은 방식으로 보호합니다.
- **레이아웃 검사를 상태별로 확장:** 가로 너비 검사에 더해 낮은 높이, 큰 글씨, 긴 결과, 보관 한도, 처리 전후 상태, 키보드 포커스와 카드 세로 경계를 확인합니다. 캡처 접근이 차단된 동안 이 자동 검사를 수동 시각 검수와 동등하게 표현하지 않습니다.

재현 오류와 실제 실행 결과는 [추가 화면 UI/UX 재검토](./OPERATIONS_UI_UX_REVIEW_2026-08-31.md)에 기록합니다.

## 2026년 9월 1일 고밀도·장시간 검증

- **기본값과 시험 부하 분리:** 공개 데모의 18,000개 이력은 유지하고, 서버 생성 수와 클라이언트 허용 상한을 벤치마크 설정에서만 100,000개로 높였습니다. 실제 사용자에게 불필요한 20MB 응답을 항상 보내지 않으면서 같은 제품 경로를 검증하기 위한 선택입니다.
- **최신 절단 대신 전체 구간 요약:** 최초 구현은 100,000개 중 최신 20,000개만 남겨 약 6분의 이력만 보존했고 DRYER-02 이상 근거가 사라졌습니다. 이 실패를 그대로 확인한 뒤 이진 탐색으로 30분 시작점을 찾고, 중간 전체 배열 복사를 피하면서 구간 경계와 센서 극값을 최대 20,000개에 담도록 바꿨습니다.
- **측정기 메모리도 제한:** 장시간 계측 배열을 브라우저에 계속 쌓지 않고 5초마다 회수합니다. CDP 강제 GC 전후 힙은 별도로 기록하되, 계측기의 GC가 관찰 구간을 반복 교란하지 않도록 시작과 종료에만 적용했습니다.
- **시간 범위 이탈을 오류로 만들지 않음:** 30분 뒤 이상 시점으로 이동하거나 작업을 발행할 수 없는 것은 안전 정책의 정상 상태입니다. 장시간 시나리오는 해당 동작을 건너뛴 횟수와 최종 발행 차단을 기록하고 나머지 확대, 이동과 실시간 추적은 계속 실행합니다.
- **CPU 제한의 표현:** 4배 CDP 제한을 물리 저사양 단말 실측으로 표현하지 않습니다. 60분 뒤 강제 GC 힙이 6.6MB 늘고 Long Task 29건이 관찰된 결과도 함께 공개하며 누수 부재나 현장 SLA를 주장하지 않습니다.

- 공개 자료 또는 저장소 코드로 사실을 확인할 수 있어야 합니다.
- TypeScript 계약, 단위 테스트 또는 E2E 사용자 흐름으로 동작을 재현할 수 있어야 합니다.
- 실제 제조 고객사 운영 경험이나 측정하지 않은 성과로 확대해서 표현하지 않습니다.
- 브라우저에서 문구, 반응형 레이아웃, 오류 로그와 핵심 행동을 확인하되 자동 검사, 실제 캡처 검수와 접근 제한으로 확인하지 못한 항목을 구분합니다.

## 제출 검토에서 수정한 선택

8월 31일에는 초기 변화량 기반 샘플러가 장력 90N 피크를 지우는 반례를 재현했습니다. 공통 시간축만 유지하면 모든 이상 신호가 보존된다는 가정은 맞지 않았습니다. 현재는 구간별 센서 극값과 경계를 합치는 방식으로 바꾸고, ECharts의 센서별 LTTB도 껐습니다. 1,800개는 정확한 출력 개수가 아닌 상한이며, 반복 횟수나 지속 시간은 요약만으로 보장하지 않습니다.

판단의 전후 근거, 제외한 대안과 AI 활용을 포함한 기여 범위는 [기술 판단 사례](./ENGINEERING_CASE_STUDIES.md)를 참고하세요. 현재 측정 스크립트는 앱의 실제 샘플러를 빌드해 호출하며 과거 알고리즘을 복사한 별도 구현을 유지하지 않습니다.

## 후속 보강: 두 설비와 전체 흐름 계측

- **진단 프로필과 안전 계약 분리:** 건조기의 표시 센서, 패널 수, 설정값과 안전 조건을 공통 화면에 전달합니다. 화면 복제보다 설정을 선택했지만 임의 센서 스키마까지 일반화하지는 않았습니다. 지원 ID, 서버 합성 입력과 테스트도 추가해야 합니다.
- **설비 전환 시 데이터 수명 분리:** 이전 데이터를 새 설비 이름 아래 표시하지 않도록 소켓과 버퍼를 교체하고 응답 및 프레임 ID를 검증합니다. 같은 브라우저의 미확인 발행 요청은 한 건만 유지해 다른 설비에서 덮어쓰지 않도록 합니다.
- **차트 단독 비교와 전체 앱 관측 분리:** 기존 전후 비교는 합성 차트의 비용을 설명합니다. 별도 opt-in 빌드에서 실제 조회와 파싱, 배치 대기, 상태 갱신, 차트 반영과 발행 저장을 측정합니다. ECharts 완료 후 두 rAF를 화면 합성이 끝난 시각으로 주장하지 않습니다. 공개 배포나 현장 네트워크의 수치도 아닙니다.
- **측정기의 의존성도 고정:** 모노레포 루트에는 Storybook이 사용하는 다른 Vite 버전이 있을 수 있습니다. 전체 앱 측정기는 웹 워크스페이스에서 Vite를 해석해 실제 앱과 같은 빌드 버전을 사용하고 버전과 소스 해시를 결과에 남깁니다.

검증된 구성과 비용은 [설비 재사용 사례](./EQUIPMENT_REUSE.md), 측정 표본과 해석 범위는 [성능 문서](./PERFORMANCE.md)에 기록합니다.
